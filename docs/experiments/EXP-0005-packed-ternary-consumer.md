## Research Question

Gate 1A: can a hardware datapath consume the canonical checkpoints' 2-bit packed ternary representation directly, sustain initiation interval 1 when data is available, and accumulate real-model dot products without any material full-weight unpacking?

Gate 1B: keeping packed weights local to memory banks, does a banked architecture reduce global weight movement relative to the streaming baseline enough to be architecturally meaningful, without a prohibitive accumulation, broadcast, buffering, control or capacity requirement?

## Hypothesis

H1/H3 (THESIS) presuppose a consumer of packed ternary data at the memory bound; EXP-0003's ceilings assume it exists and is cheap. H6 (co-design) adds that the consumer must operate on the compressed form (EXP-0004: compression that is expanded before use saves nothing in traffic). Hypothesis tested: both a central streaming consumer and a bank-local consumer can be built from Y-Core with state proportional to outputs, not to N × K, and bank-local placement removes the ternary weight stream from the global path at the cost of activation delivery, output return and resident capacity.

## Why It Matters

For Falcon-E 1B the ternary stream is 396 MB per token (68% of global bytes at 2k context in EXP-0003). If it can be consumed where it resides, the system's global bottleneck moves to the head and KV cache, which EXP-0004 showed can be ~4-bit. If not, FlexTern's advantage stays a bandwidth multiplier on a conventional streaming design.

## Setup

**Packing re-verified from code and data (MEASURED):** `analysis/safetensors_reader.py` (transcribed from transformers' BitNet integration and validated on all three checkpoints in EXP-0002/0002B): packed shape `[N/4, K]` uint8, `packed[r, c]` bits `[2i+1:2i]` = code of `W[i·N/4 + r, c]`, code = q + 1 (00 = −1, 01 = 0, 10 = +1, 11 unused; code 3 occurs 0 times in 2.08 B BitNet weights). One byte = four OUTPUT rows at ONE input position; consecutive bytes walk K. (code − 1) mod 4 is exactly the ADR-0002 Y-Core encoding, so decode is a 2-bit decrement; checkpoint 11 maps to Y-Core's reserved 10 and contributes 0 (deterministic, tested).

**Modules (all new, `rtl/`):** `ternary_unpack4` (byte → four Y-Core codes + reserved flag); `sum_tree` (balanced signed adder tree, width grows one bit per level); `y_stream_engine #(BYTES, ROWQ, ACC_W)` (ROWQ row streams × BYTES bytes per cycle = 4·ROWQ·BYTES terms, 4·ROWQ accumulators, valid/ready both sides, runtime K and N, two pipeline stages); `y_memory_bank #(BYTES)` (address generator + 4-entry FIFO + engine with ROWQ = 1 over a bank-local synchronous weight memory that is a PORT, not contents); `y_near_memory_engine #(NB, BYTES)` (NB banks owning contiguous row-quad blocks for all K, per-bank activation ports, fixed-priority result collector); `int4_stream_baseline #(BYTES)` (controlled INT4 structural baseline, 2 rows per byte, `*` products, 25-bit accumulators). Activation buffers (K × 8 bits) are external ports on every engine so synthesis reports logic only and memory is accounted analytically.

**Dataflow choice:** contiguous bytes run along K within one packed row, so the native consumer is "row-quad": each byte feeds four accumulators at one k; BYTES consecutive bytes feed the same four accumulators with BYTES terms each (K-parallel within the row-quad). Output parallelism beyond four rows needs ROWQ separate address streams strided by K bytes, which a single linear memory does not provide but banked memory does: the near-memory engine is NB such streams. Both forms were built and synthesized (ROWQ = 1 and ROWQ = 4, 64) so the comparison is explicit. No transpose or repack exists anywhere.

**Reference and vectors:** `analysis/hardware_gate/reference.py` imports the profiler's pack/unpack, computes exact-integer golden results, and writes case files. Synthetic cases (seeded 20261007, regenerated by the tests, not committed): random matrices and accumulator extremes for every K ∈ {2048, 2560, 6912, 9216, 13312}; reserved-code injection; a 13-row-quad tail; INT4 cases. Checkpoint slices (bytes written to `build/` only; provenance in `results/hardware_gate/checkpoint_slices.json`): Falcon-E 1B layer-0 `k_proj` full tensor [64, 2048] and `down_proj` rows 0–7 [8, 9216]; Falcon-E 3B `down_proj` [8, 13312]; BitNet 2B4T `q_proj` [8, 2560] and `down_proj` [8, 6912].

### R4. Cycles, utilization and required clocks on the real workloads (ANALYTICAL from measured shapes; `workload_totals.csv`, `bandwidth_requirements.csv`)

Falcon-E 1B per token: 6,193,152 cycles at 256 terms/cycle, 1,548,288 at 1024 (streaming, utilization 1.0 because every K is a multiple of 256 and every N a multiple of 4·ROWQ for ROWQ ≤ 16); 64 banks × 16 B: 387,072 cycles (utilization 1.0). Beyond that the fixed-priority collector, which emits one four-row group per cycle, becomes the limit: a tensor cannot finish in fewer cycles than it has row-quads, so once NB · b exceeds K the K = 2048 tensors (71% of Falcon-E weights) are collector-bound. 256 banks × 16 B: 168,960 cycles (utilization 0.57); 1,024 banks: 155,136 (0.16); 64 banks × 64 B: 165,888 (0.58). The floor is Σ row-quads per token = 150,528 for Falcon-E 1B regardless of bank count. Falcon-E 3B and BitNet follow the same pattern (BitNet 0.99 at 64 banks × 16 B because of its 160-row-quad `k/v_proj`, 0.67 at 256 banks). A hierarchical or wider collector would be needed before hundreds of banks pay off in cycles; the byte accounting in R5 is unaffected.

Required clock = target bandwidth ÷ packed bytes per cycle, **UNMEASURED TARGETS**: 64 B/cycle → 1,562.5 MHz for 100 GB/s, 3,906 MHz for 250 GB/s; 128 B/cycle → 781 / 1,953 MHz; 256 B/cycle → 391 / 977 / 1,953 MHz (500 GB/s). Near-memory aggregate 64 banks × 16 B = 1,024 B/cycle → 97.7 / 244 / 488 MHz. Absolute line rate remains UNMEASURED; no FPGA target exists.

## Interpretation

- **Gate 1A (INFERRED from R1–R3): the checkpoint packing is hardware-native.** Four output rows per byte at one K position makes a row-quad engine the natural consumer: BYTES contiguous bytes per cycle feed four accumulators, no transpose, no repack, decode is a 2-bit decrement. Initiation interval 1 is a cycle-counted fact in simulation at every K, and the only state is 4·ROWQ accumulators plus pipeline registers. Output parallelism beyond four rows is not free on a linear stream: it needs strided address streams, 4× the flip-flops at equal throughput (R3), and belongs to banks, not to a central engine.
- **Cost structure (INFERRED):** at 96–115 cells per term the engine is dominated by accumulation (the Y-Cores are 33 cells each, about a third); this is EXP-0001's "accumulation dominates" observation at 16–64× the scale, and the ratio to the INT4 structural baseline settles at 2.7× rather than the 12× of the primitive. Longest paths of 42–51 gates for the single-cycle 64–256-input trees say nothing about frequency but do say the trees would need pipelining in any physical implementation.
- **Gate 1B (INFERRED from R5–R7): bank-local compute removes the ternary weight stream from the global path, and the price is explicit.** With bank-local activation buffers, global bytes fall >140× for the ternary part; the whole system's global bytes fall 1.4–13× depending on context and head/KV precision, and the limiter becomes the non-ternary path. The costs: (1) whole-model residency, 396–730 MB near compute, which no technology is chosen for here; per-layer residency gives nothing; (2) activation delivery NB × K per matvec (23.6 MB per token at 64 banks, 6% of the weight bytes; 377 MB at 1,024 banks, 95%); (3) NB × 13 KB of buffers, or, without them, a broadcast equal to the weight bytes; (4) a collector that serializes NB results (NB + 3 cycles per operation) and bank utilization that falls below 0.6 at 1,024 banks for the small GQA projections. Local reads never disappear: every weight byte is read every token.
- **Format attribution (INFERRED):** near-memory helps INT4 exactly as much in global bytes; ternary's specific contribution is half the local bytes, half the capacity and 2.7× fewer cells per term. A fair system claim must therefore compare a ternary near-memory design against an INT4 near-memory design, not against a streaming one.
- **Required clocks (ANALYTICAL):** 100 GB/s needs 1.56 GHz at 64 B/cycle or 391 MHz at 256 B/cycle for one streaming engine; a 64-bank near-memory array at 16 B per bank needs 98 MHz for the same aggregate, and that is the largest configuration at which the real shapes keep every bank busy (R4): the one-group-per-cycle collector caps throughput at one row-quad per cycle, so more banks than K/b buy nothing in cycles without a collector redesign. These are requirements on an unmeasured implementation.
- **Zero handling (MEASURED):** zeros contribute 0 through Y-Core's three-way select; 40% of the real weights are zero (EXP-0002B) and the engines neither skip them nor gain bandwidth from them, and no such saving is claimed.

## Surprises

1. The decode is a 2-bit decrement: the checkpoint code minus one is exactly the ADR-0002 Y-Core encoding, so "unpacking" costs 15 cells per byte.
2. The output-parallel form that the EXP-0005 brief suggested as the natural dataflow is the expensive one on a single stream (3× the cells, 41× the flip-flops at equal throughput) because every one of its 256 accumulators adds one term per cycle; the row-quad K-parallel form is the cheap one. Output parallelism is what banks provide.
3. Lockstep activation broadcast without bank buffers costs exactly the weight bytes it was meant to save.
4. Utilization on the real shapes is 1.0 for every streaming configuration up to 16 row streams and for near-memory up to 64 banks × 16 B (0.99 for BitNet): the canonical models' K (multiples of 256) and N (multiples of 256) fit without tails. What limits larger bank counts is not tails but the collector: with one result group per cycle, a 2048-wide tensor needs at least N/4 cycles whatever the bank count, so 1,024 banks run at 16% utilization. The reviewer caught this; the first draft of the cycle tables had ignored it.
5. The canonical YoWASP Yosys asserts on `hierarchy -chparam` with recursive modules and is ~20× slower than native Yosys 0.52 (KI-008).

## Limitations

- Generic synthesis only: cells are structure counts, not area, frequency or power; no FPGA, no standard-cell library, no constraints. Required clocks are targets.
- Memories are ports: no SRAM macro, no bank read energy, no routing of the activation broadcast or the result collector were modeled; capacity is bytes only.
- Single-cycle adder trees of up to 256 inputs (longest path 51 gates) are structurally unrealistic at the required clocks and would be pipelined; II = 1 is unaffected by pipelining, latency is.
- The near-memory top was synthesized at NB = 4 only; larger NB are scaled analytically from one bank plus the measured collector. The fixed-priority collector drains one result per cycle, which bounds NB ≤ K/b before results back up (not reached in the simulated cases).
- Traffic is batch 1, stream-once, with 32-bit outputs; activation injection assumes INT8 activations arrive once per distinct input vector; weight preload is untimed.
- Memory-interface asymmetry: bank weight memories are modeled as synchronous one-cycle reads behind a FIFO, while the activation buffer read is combinational on both engines (a real SRAM adds a pipeline stage to it); the streaming testbench is a zero-latency source. If anything this favors the streaming engine's cycle count.
- Reproducibility across Yosys versions: the sweep is Yosys 0.52; see R3 for the 0.69 cross-check status.
- The RTL test suite was run in chunks after the harness killed background runs under host memory pressure (KI-007); every class passed in a foreground run.

## What This Proves

- MEASURED: RTL exists that consumes the canonical 2-bit packing directly, at initiation interval 1, with correct results on all five K values, accumulator extremes, reserved codes, tails, backpressure, consecutive operations, and real checkpoint slices from all three models, with state independent of N × K (333 flip-flops at 256 terms/cycle).
- MEASURED: that engine costs 25.5k generic cells at 256 terms/cycle (96–115 cells/term from 64 to 1024 terms/cycle) with no multiplier, versus 69.5k for an INT8 × INT4 structural baseline at equal throughput.
- MEASURED: a bank-local version with the same arithmetic produces bit-identical results, reads every weight byte locally and none globally during inference, and costs 147 → 123 cells/term at 64 → 256 terms per bank plus a collector.
- ANALYTICAL: on Falcon-E 1B, bank-local placement cuts global bytes per token from 399 MB to 2.8 MB for the ternary part, if 396 MB stay resident; the system's global limiter then becomes the head and KV cache; activation delivery costs NB × K per matvec with buffers and the full weight-byte count without.

## What This Does NOT Prove

- Any frequency, bandwidth, energy, area or tokens/s. **Fmax, FPGA utilization and physical bandwidth were not measured because no FPGA target is available.**
- That hundreds of megabytes of near-compute memory are economical in any technology; that bank reads are cheaper than fabric reads in energy; that the activation broadcast or the collector route at scale.
- Anything about the head or the KV cache consumer (Q-022), which this experiment leaves as the system limiter.
- Competitor comparisons of any kind. The INT4 baseline is a structural RTL baseline, not a GPU.

## Gate verdicts

**Gate 1A — PASS at the STRUCTURAL / CYCLE level.** Packed ternary consumption works at II = 1 in RTL and generic synthesis, with no persistent full-weight expansion; absolute Fmax and physical bandwidth remain UNMEASURED.

**Gate 1B — PASS at the DATAFLOW / GLOBAL-TRAFFIC level.** Bank-local compute removes the ternary weight stream from the global path (>140× fewer global ternary bytes, 1.4–13× fewer total global bytes depending on context and head/KV precision) with no partial sums, bounded broadcast (NB × K per matvec with 13 KB buffers per bank) and bounded control; physical area, energy, timing, routing and the memory technology for 396–730 MB of residency are INCONCLUSIVE and recorded for FPGA/ASIC-targeted validation later.
