# EXP-0012 — Ternary predictive-state architecture for robotics (algorithmic feasibility)

Status: **in progress** (Stage A done, protocol locked; see "Lock" below). Branch `exp-0012-predictive-state`, not merged to main.
Authorized by the founder directive of 2026-11-07. Owner: Claude (implementation); founder + ChatGPT (direction).
Literature review: `EXP-0012-literature-review.md`. Protocol (machine-readable): `analysis/predictive_state/protocol_v1.json`.

## Research question
Does persistent state + JEPA-style latent prediction + ternary-weight computation give a meaningful, *separable* advantage in inference cost for a partially observable manipulation task, against competent FP16, INT8, INT4 and non-recurrent controls? Four sub-questions (A persistent state, B JEPA, C ternary, D adaptive perception) are tested separately (`protocol_v1.json: questions`).

## Starting evidence from earlier experiments (read before designing; not reinterpreted)
- EXP-0011 (MEASURED, CPU): native ternary was **not** faster than quality-matched INT4 at the runtime level (SPEED_LOW, geomean end-to-end 0.73). Ternary hardware benefit must therefore be argued from bytes and logic, not from existing CPU kernels.
- EXP-0003 (ANALYTICAL): ternary specialization is bounded by the non-ternary share of per-step cost (Amdahl). The same logic is applied here before any training: see "Analytical ceilings".
- EXP-0001/0005 (MEASURED, generic synthesis): ternary dot products need no multiplier (~2.7x fewer cells than INT8xINT4 at 256 terms). EXP-0008/0009 (ANALYTICAL): resident-SRAM read energy and retention leakage are temperature-dependent open questions. No hardware work is authorized here.

### Benchmark: OccPick2D (`analysis/predictive_state/env.py`)
Point end-effector, continuous 2D action + gripper, 32x32 RGB top-down render with pixel noise, proprioception (position, held flag, gripper state) and a task code (target colour). Picks the target among distractors and places it in a fixed goal zone.
- Partial observability: 2-3 static occluders hide objects; **camera blackouts** (frames lost, flagged); the target is always visible at t=0, so remembering it is possible.
- Disturbance: **unexpected displacement** of the target by 0.25-0.40 units at a random step (drops it if held), possibly during a blackout.
- Held-out generalization: layout ids (occluders + goal) in disjoint ranges for train/dev/test; test HARD uses 4 distractors (train has 1-3). LONG: five sequential picks (5x the single-pick horizon, up to ~400 steps) with the recurrent state never reset.
- Success: target released inside the goal zone before the 80-step pick limit; wrong object picked ends the episode.
- Validation before any learned policy (MEASURED on 200 test-split episodes per condition): the privileged expert succeeds 100% in NOM, OCC, DIST, HARD and LONG (5/5 picks); a do-nothing policy scores 0% (unit tests).

**What it cannot establish:** real contact dynamics, 3D grasping, camera/lighting realism, real encoders (a 0.83 M-MAC CNN stands in for a vision backbone, so the encoder/updater cost ratio is a property of this toy, not of real VLAs), or any real-robot result. Simulated results are not real-robot validation.

### Baselines and candidates (`protocol_v1.json: arms`)
R (single frame) and S4 (4-frame stack) are the conventional reactive controllers; T16 is a causal transformer over a 16-step latent history; G0 is a GRU without JEPA; G is the FP16 GRU + JEPA (this is both Baseline B and Baseline D: recurrent state with the same encoder, run at every step). INT8/INT4 QAT recurrent controls and the ternary candidates (updater-only E1, encoder+updater E2) are trained with QAT under the same budget. The adaptive Candidate F and its FP16/INT4/INT8 controls are inference-time triggers on those checkpoints (the random observation-dropout used in training makes every recurrent arm able to run on skipped frames). All arms train by behaviour cloning on the same demonstrations, because a fair comparison needs one training regime; RL or latent-space planning is **not** attempted (a CEM/MPC planner on the predictor is left as a possible follow-up, not a part of this prototype).

### Analytical ceilings (ANALYTICAL; computed before any training; `cost_model.py`)
Per control step at full perception: the encoder is 85% of MACs (831k of ~977k) for the recurrent arms; the GRU updater + heads are ~12%. A ternary updater therefore changes MAC count by 0 (a ternary MAC is an add, same count) and reduces weight bytes only; skipping the encoder is the only route to a >1.2x MAC reduction. In weight+state bytes the encoder is 55-91% of the step depending on how the encoder is quantized. Ternary vs INT4 on the same scope can give at most ~2x on weight bytes (2 vs 4 bits) and less once state, scales and the trigger head are included, so the G4 ">=2x vs the strongest conventional quantized control" bar is near the arithmetic limit before any model quality is considered. Exact table: `results/predictive_state/cost_table.md` (written at the end).

## Amendments
All three were made after the lock and before any TEST-split measurement; every pre-amendment run is kept in `results/predictive_state/stage_b_history/`. Dev numbers below are single seed (seed 0), ~100 episodes per cell, so differences of ~0.1 are within noise.

**Amendment 1 (Stage B, floor effect): task-conditioned CoordConv encoder.** First Stage B pass (dev, original architecture, protocol-compliant data): **every arm sat at 0-20% success** (NOM/OCC/DIST/HARD: R .19/.05/.10/.00; S4 .20/.13/.15/.03; T16 .15/.14/.14/.02; G0 .20/.14/.12/.08; G .17/.20/.19/.10). The locked gate G0 (discrimination) could not be evaluated meaningfully. Diagnosis: closed-loop rollouts on easy dev/train conditions (no blackout, no displacement, one distractor) still gave 11-23% success, the median closest approach to the target was 0.095 (pick radius 0.06), so the failure was navigation to the target, not memory. A supervised localization probe (`diag_localization.py`, MEASURED on round-0 training frames) found the unconditioned encoder could not localize the target by colour: median error 0.110 (22.6% of frames within 0.05) versus 0.0175 (91.6%) for an encoder that receives the task code as broadcast channels plus x/y coordinate channels. A DAgger-style aggregation (1500 extra episodes labelled by the expert, `dagger.py`) was tried first on the *unconditioned* encoder and did **not** help (R .09/.01/-/.00, S4 .17/.05/-/.03, T16 .10/.06/-/.00 on NOM/OCC/DIST/HARD); it is retained as a negative result and not used. The conditioned encoder is now part of every arm (the cost model charges the extra first-conv channels). Dev, conditioned encoder, original data: R .63/.37/-/.21 (NOM/OCC/HARD), S4 .22/.13/-/.08, T16 .72/.56/-/.41, G .40/.44/-/.28.

**Amendment 2 (Stage B): feed-through of the current embedding into the recurrent policy head.** With amendment 1 the GRU policy (head sees only h) was below the reactive policy on NOM (.40 vs .63): a 128-d gated state is a poor channel for precise localization. The policy head of the recurrent arms now also receives z_t x valid_t (zeros on skipped or blacked-out frames), as the reactive and transformer controls already see their embeddings. Dev, G: .63/.51/-/.39 (NOM/OCC/HARD). The change leaves the encoder-skipping logic intact (a skipped step feeds zeros) and is applied to every recurrent arm.

**Amendment 3 (G5 definition, before any test measurement): LONG is 10 picks, not 5.** A successful 5-pick episode lasts ~200 steps, so the locked "steps > 300" probe window would be empty. LONG now has 10 sequential picks (~400 steps, 2.5x the 160-step training length, no state reset); the late probe window is steps > 160 (beyond the training length) and the early window is steps <= 100. The LONG success metric is full completion of all 10 picks and mean fraction of picks completed.

Known limitations recorded at this point: S4 (4-frame stack) underperforms the single-frame R in the dev checks; I did not find the cause, so it should not be read as "frame stacking is worse in general". T16 (transformer over 16 latents) is a strong control.

**Amendment 4 (Stage B, seed variance / under-training): 6000 steps x batch 48 for every arm (was 3000 x 24).** After amendments 1-3 all 33 locked-budget checkpoints (3 seeds) were trained and evaluated on DEV (~100 episodes per cell). Result: **seed 0 looked fine but seeds 1-2 did not**: R NOM .63/.22/.32, G NOM .63/.30/.24, T16 NOM .72/.16/.46 (seeds 0/1/2), so means over seeds were ~.3-.4 with seed spread of 0.3-0.5 absolute; the locked G0 discrimination gate (G minus max(R,S4) on OCC/HARD >= 0.15) gave +0.11 and G1 (macro >= 0.60) would fail. (All of this is in `results/predictive_state/stage_b_history/amend3_dev_3000x24_seed*.json`.) The cause looked like under-training of behaviour cloning rather than architecture, so a bounded diagnostic with the cheap controls R and T16 on seeds 1-2 (dev NOM/OCC, `tune_*.json`) compared three budgets: lr 1e-3 x 6000 x 24 (R NOM .66/.42, T16 .47/.74), lr 5e-4 x 6000 x 24 (R .45/.33, T16 .46/.46), lr 2e-3 x 6000 x 48 (R .67/.79, T16 .69/.64; OCC .55/.63 and .57/.54). The last is adopted for **all** arms and seeds (a 4x larger sample budget). No other hyperparameter was tuned, and nothing was tuned on TEST. Cost: GRU arms take ~4x longer, so **G-I8a and G-Ta-s8 are trained for seed 0 only** (their roles are secondary: a conventional INT8 reference and a state-precision ablation); every other arm has seeds 0-2. All amendment-3 checkpoints are discarded from analysis but kept in the history files.

**Amendment 5 (measurement fairness and decision rules, committed before any TEST measurement; `protocol_v1_amended.json`).** (a) The fixed-rate trigger is now a fractional accumulator whose rate is bisected on DEV against the *measured* encoder fraction, exactly like the pixel-difference and learned triggers (the first version solved k = 1/budget analytically and would have under-spent the budget because blackout steps cannot be encoded, tilting the comparison toward the learned trigger); measured encoder fractions are reported beside every matched-budget comparison. (b) The state probe was rebuilt: standardized features, cross-validated ridge, 150 rollouts, with positive controls (h and z to target on valid frames) and a goal probe, because the first version gave R^2 0.03 early / 0.33 late on 834 rows. (c) LONG success fraction is picks / 10 and per-pick conditional success is reported as the drift diagnostic. (d) Two exploratory long-blackout conditions (BLK40, BLK40D: blackouts of 30-50 steps) are added **after** the dev check showed persistent state gave no advantage under the locked conditions (G minus R on OCC/HARD about 0 to +0.1 at 300 dev episodes, seeds 0-1); they are post-hoc, labelled exploratory, and not part of any gate. (e) Decision rules fixed before test: amendment 4 is the last fix attempt for the baseline floor; the locked G0 discrimination gate is evaluated on DEV with the amendment-4 checkpoints at 300 episodes per cell; if it fails the verdict is STOP per the locked rules and questions A-D are reported as descriptive, ungated results (I will still state what the descriptive numbers suggest, separately labelled as interpretation). (f) Seed 2 of some arms trains after this commit; its checkpoints are hashed in a follow-up amended-lock commit before its test evaluation. G-I8a and G-I4u are not trained for seed 2 if time does not permit (recorded then).
