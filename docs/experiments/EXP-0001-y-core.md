# EXP-0001 — Y-Core v0.1 and Y-Dot16 vs INT8 multiply baseline (generic synthesis)

Status: Complete

## Research Question

Can activation × ternary-weight be implemented correctly in RTL without a general multiplier, and how does the resulting generic logic compare to a conventional signed INT8 × INT8 multiplier, at single-element and 16-element dot-product scale?

## Hypothesis

H1 from `../THESIS.md`: a dedicated ternary datapath is materially smaller than a multiply-based datapath at the same activation precision.

## Why It Matters

This is the most basic test of the FlexTern thesis. If the primitive advantage were absent at the logic level, the thesis would have to rest entirely on memory/encoding effects.

## Setup

Four combinational RTL modules, all in `rtl/`:

| Module | Function | In | Out |
|---|---|---|---|
| `y_core` | x × w, w ∈ {-1,0,+1} | 8-bit signed act, 2-bit weight | 9-bit signed |
| `int8_mul_baseline` | x × w, w any INT8 | 8-bit signed × 8-bit signed | 16-bit signed |
| `y_dot16` | Σ 16 Y-Core terms | 16 × (8-bit, 2-bit) | 13-bit signed |
| `int8_dot16_baseline` | Σ 16 INT8 products | 16 × (8-bit, 8-bit) | 20-bit signed |

Interface parameters fixed by ADR-0002. Weight encoding 00=0, 01=+1, 11=-1, 10=reserved→0.

## Baseline

Signed INT8 × INT8 via the Verilog `*` operator, and a 16-element dot product built from it with the same adder-tree structure as Y-Dot16. Chosen because INT8 is the most common conventional low-precision inference datapath. It is a generic RTL baseline, not a model of any commercial MAC unit. It computes a strictly more general function than Y-Core with a wider output, which must be remembered when interpreting ratios.

## Method

1. Python golden reference `reference/ternary_op.py`; 19 unit tests in `tests/test_reference.py`.
2. Y-Core exhaustive testbench: all 256 activations × 3 valid weights = 768 cases, expected values computed with 32-bit integer math in the testbench; plus 256 cases of the reserved encoding; plus -128 × -1 as a named check.
3. Y-Dot16 testbench: 26 deterministic cases (spec example, all-boundary vectors, alternating patterns, each lane alone at -128 × -1), 10,000 `$urandom` vectors, and 2,000 vectors generated by `scripts/gen_vectors.py` from the Python reference and loaded via `$readmemh`.
4. INT8 baseline testbench: 65,536 exhaustive products, 7 deterministic dot16 cases, 10,000 random dot16 vectors.
5. Mutation check: Y-Core's negate path was deliberately broken in a scratch copy; the testbench reported 256 mismatches and exited non-zero.
6. Yosys scripts in `synth/`: `read_verilog -sv; hierarchy; proc; [flatten]; opt_clean; stat` (coarse cells, answers "was `$mul` inferred") then `synth -top X -flatten; stat` (generic gates). `$scopeinfo` marker cells are deleted before each `stat` so counts are logic only.
7. Entire flow reproduced by `scripts/run_all.ps1`, which reports PASS only on exit code 0 plus the testbench's success token.
8. Steps 6 repeated under WSL with Yosys 0.52 as a tool-version sensitivity check.

## Metrics

Coarse cell types before mapping (specifically presence of `$mul`); total generic gate-level cells after `synth -flatten`; XOR/XNOR and MUX subtotals; simulation pass/fail with case counts.

## Interpretation

- **MEASURED:** The ternary primitive synthesizes to decode + negate + select with no multiplier, as designed.
- **MEASURED:** The ternary datapath is several times smaller in generic cells at both scales and in both Yosys versions. H1 is supported at the generic-logic level.
- **MEASURED:** The ratio shrinks from element level (7–12×) to dot-product level (5–6.5×). The shared accumulation cost dilutes the per-element advantage.
- **INFERRED:** Roughly 60% of Y-Dot16's logic is the 13-bit adder chain, not the Y-Cores. Further savings at this level would come from accumulator structure (narrower partial sums, carry-save, or sparsity-aware accumulation), not from the primitive.
- **INFERRED:** Tool-version sensitivity is large on small designs (Y-Core 33 vs 60) and small on large ones (dot16 within 3%). Only the large-design ratio should be treated as semi-stable.

## Surprises

- The Yosys 0.69 WebAssembly build took ~13 minutes on the 16-multiplier baseline where native 0.52 took under 3 seconds. ABC under WASM appears pathological on that netlist. Disabling ABC drops it to 2 seconds (8,973 cells, unoptimized). Recorded as KI-001.
- The OSS CAD Suite native Windows Yosys is blocked outright by Smart App Control (unsigned binary). The YoWASP build avoids this by running inside signed Python. Recorded as KI-002.
- Yosys 0.69 produced a smaller Y-Core (33) than 0.52 (60), an almost 2× swing from tool version alone on a 4-coarse-cell design.

## Limitations

- Generic cells are not area, delay, or power on any technology. FPGA LUT packing and ASIC cell libraries would both change the numbers and probably the ratios.
- The baseline computes a strictly more general function with a wider output. An INT8 datapath carrying only ternary values would be wasteful by construction; the comparison shows the cost of generality, not a flaw in multipliers.
- Combinational only. No timing, no pipelining, no clock. Critical path was not measured.
- 16 elements is small. Memory, control, and interconnect, which may dominate at system scale, are absent.
- One activation width (8-bit). Different widths would shift the balance between element cost and accumulation cost.
- Ternary models need more parameters than INT8 models for equal quality. This experiment does not account for that, so per-element savings do not translate directly to per-model savings.

## What This Proves

- Y-Core v0.1 is correct across its whole valid domain, including the 9-bit corner case.
- Y-Dot16 is correct against both testbench arithmetic and an independent Python implementation.
- Ternary × activation needs no multiplier, and a generic synthesizer confirms none is inferred.
- At the generic-logic level, the ternary datapath is roughly 5–12× smaller than an INT8 multiply datapath depending on scale and tool version.

## What This Does NOT Prove

- Anything about GPUs, tokens/sec, tokens/watt, cost, frequency, ASIC area, or FPGA utilization.
- That the advantage survives once memory traffic, control, and a real workload are included.
- That the measured ratio is a property of the architecture rather than of this baseline choice and this tool.
